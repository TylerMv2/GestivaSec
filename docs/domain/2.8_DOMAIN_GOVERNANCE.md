## 1. Resumen Ejecutivo

La subfase **2.8 Domain Governance** establece las reglas de gobierno, principios de soberanía de modelos, matriz de propiedad y patrones de **Capa Anti-Corrupción (Anti-Corruption Layer - ACL)** que regirán la relación entre los dominios y Bounded Contexts de **GestivaSec V1**. Este documento garantiza el aislamiento conceptual, la inviolabilidad de las reglas Multi-Tenant y la prohibición de contaminación de modelos entre dominios o con servicios de terceros (Cloudflare, Vercel, Supabase).

---

## 2. Governance Principles (Principios de Gobierno de Dominio)

1. **G-01: Soberanía de Modelo por Bounded Context**: Cada Bounded Context posee autoridad exclusiva sobre su modelo de dominio. Ningún contexto puede consultar o mutar directamente las entidades internas de otro contexto.
2. **G-02: Comunicación Basada en Eventos e Interfaces Explícitas**: La colaboración entre dominios se realiza únicamente mediante la publicación y suscripción de Eventos de Dominio Inmutables (`DomainEvents`) o llamadas a Interfaces de Puertos formales.
3. **G-03: Inviolabilidad de Aislamiento Multi-Tenant**: Toda entidad, comando, consulta o evento debe incluir de forma mandatoria el identificador inmutable de organización `tenant_id`.
4. **G-04: Independencia Tecnológica del Dominio (Pure Domain)**: El código del dominio debe mantenerse 100% libre de bibliotecas de persistencia, frameworks web, decoradores de ORM o referencias a APIs externas.

---

## 3. Anti-Corruption Rules & Layer (Capa Anti-Corrupción - ACL)

Para evitar la contaminación del modelo central por formatos o APIs de terceros, se imponen las siguientes reglas ACL:

```
┌─────────────────────────────────────────────────────────────────────────────────────────┐
│ CAPA ANTI-CORRUPCIÓN (ACL) EN GESTIVASEC V1                                             │
├─────────────────────────────────────────────────────────────────────────────────────────┤
│ API / Formato Externo (Cloudflare / Vercel / Supabase API)                              │
│                                           │                                             │
│                                           ▼                                             │
│ ┌───────────────────────────────────────────────────────────────────────────────────┐   │
│ │ CAPA ANTI-CORRUPCIÓN (ACL Translator / Adapter)                                   │   │
│ │ Traduce payloads HTTP/JSON de terceros a Objetos de Valor e Entidades puras       │   │
│ └─────────────────────────────────────────┬─────────────────────────────────────────┘   │
│                                           │                                             │
│                                           ▼                                             │
│ Modelo de Dominio Puro (AssetAggregate / SyntheticProbeAggregate / ValueObjects)        │
└─────────────────────────────────────────────────────────────────────────────────────────┘
```

- **ACL-01 (Aislamiento de APIs de Proveedores)**: Los datos telemétricos recibidos de Vercel Edge Runtime, Cloudflare API o Supabase Cloud deben ser traducidos en la frontera del sistema por una `AntiCorruptionLayer`, impidiendo que los esquemas JSON del proveedor contaminen las entidades del dominio.
- **ACL-02 (Traducción de Errores de Red)**: Los códigos de error nativos de red (ej. socket timeouts de SO, codigos HTTP de NGINX/Vercel) deben ser encapsulados en Objetos de Valor de la capa de dominio (`ProbeExecutionResult`, `LatencyMs`).

---

## 4. Cross-Domain Policies (Políticas Inter-Dominio)

- **POL-01 (Política de Declaración Automática P1)**: La emisión del evento `SyntheticCheckFailed` por parte de `BC-01` obliga a `BC-02` (Incidentes) a declarar inmediatamente un expediente de incidente P1 en estado `DECLARED`.
- **POL-02 (Política de Inmutabilidad de Auditoría)**: Todo evento de dominio emitido por `BC-01`, `BC-02`, `BC-03` o `BC-04` debe ser capturado de forma asíncrona por `BC-05` (Auditoría) para su persistencia inalterable.
- **POL-03 (Política de Enrutamiento RACI)**: La notificación de alertas producidas por `BC-01` o `BC-02` debe filtrarse contra la Matriz RACI guardada en `BC-06` para despachar mensajes exclusivamente a los roles autorizados.

---

## 5. Domain Rules (Reglas Inmutables de Dominio)

- **DR-01**: Ningún activo puede ser monitoreado sintéticamente si se encuentra en estado `DECOMMISSIONED` en el inventario (`BC-04`).
- **DR-02**: Ningún incidente de severidad P1 puede cerrarse en `BC-02` sin un informe RCA validado por el responsable asignado.
- **DR-03**: Todo `AuditLogRecord` creado en `BC-05` es inmutable y no expone métodos de modificación ni borrado.

## 6. Ownership & Decision Matrix

| Bounded Context | Propietario de Negocio (Owner) | Dominio de Decisión Exclusiva | Regla Anti-Corrupción Aplicada |
| :--- | :--- | :--- | :--- |
| **BC-01 (Observabilidad NOC)** | Ingeniero NOC | Frecuencia de sondeo y estados de latencia | `ACL-02`: Aislamiento de sockets de red. |
| **BC-02 (Incidentes & RCA)** | Analista SOC / NOC | Flujo de estados P1-P4 y validación RCA | Invariante inmutable de cierre RCA. |
| **BC-03 (Seguridad SOC)** | Security Architect | Clasificación OWASP / MITRE ATT&CK | `ACL-01`: Traduce WAF rules a Findings. |
| **BC-04 (Inventario)** | DevSecOps | Fuente de verdad de activos y URLs | Validación estricta de dominios autorizados. |
| **BC-05 (Auditoría Inmutable)**| Auditor / CTO | Criterios de no repudio e inmutabilidad | Aislamiento total de escritura destructiva. |
| **BC-06 (Identidad / Tenant)** | DBA / Plataforma | Asignación de RBAC e inyección de TenantId | Verificación obligatoria de `tenant_id`. |
| **BC-07 (Notificaciones)** | DevSecOps / SRE | Reglas de desduplicación y canalización | Aislamiento de transporte de mensajería. |
